Forks

A fork is your own copy of a repository's branches and tags: you can push to it freely, without write access to the original, and offer your changes back with a merge request.

Forking

Fork in the repository header (shown when you're signed in, the repository allows forks, and you have somewhere to fork it to) opens the fork form:

  • Owner: your account or an organization where you can create repositories, except the original's own owner. To change a repository in your own account, push a branch to it instead; you can fork it only into an organization.
  • Name: the original's name unless you change it. If you already have a repository with that name, the form suggests a free one.
  • Who can see this repository: the original's visibility at most. A fork of a private repository is private, and stays so even if the original is deleted.
  • Copy only the default branch: leaves the other branches behind (tags in the default branch's history still come along).

The fork opens right away. Its branches and tags are copied in the background, usually within a second; until then the page says so and pushes to it are refused. Merge requests, issues, and the original's settings aren't copied.

A fork shows Forked from with a link to the original (or "a deleted repository"). Forks of a repository (/<owner>/<repo>/forks, linked from the fork form) lists the forks you can see.

Keeping a fork up to date

On a fork's front page, a line compares its default branch with the original's: up to date, or how many commits it's ahead and behind. If it's behind, Sync fork brings it forward, without a clone on your side.

If both have their own commits, the branch can't simply move forward: Sync fork explains this and offers to discard your commits (it asks for your password again). To keep them, push them to another branch first. Branch protection in your fork applies to syncing like to a push.

With a token (repo:write), POST /api/v1/repos/{owner}/{repo}/sync with {"branch": "main"} does the same; it answers fast_forwarded, created, up_to_date, or diverged with the counts, and "discard": true drops your commits. GET .../fork includes ahead and behind for the default branch.

What a fork contains

Only branches and tags. The fork doesn't depend on the original: it keeps working when the original is cleaned up or deleted. Commits that were only on branches the original deleted aren't copied, except those of recent large pushes until the fork's own maintenance removes them.

Losing access to the original

A fork of a private (or internal) repository depends on your access to it. If you lose read access to the original, your fork is locked: nobody but site administrators can see or clone it. When you get access back, the fork is unlocked as it was. A fork that stays locked for the instance's retention period (7 days by default) is deleted. A fork of a public repository is never locked, even if the original later becomes private. For a fork in an organization, the access of whoever created it counts.

Merge requests from a fork

To propose your fork's changes to the original, open a merge request against the original with your fork as the source. Clone your fork (here Bob's fork bob/demo of alice/demo):

git clone https://slath.example/bob/demo.git bob-demo && cd bob-demo

jj git clone https://slath.example/bob/demo.git bob-demo && cd bob-demo

Then commit your work and push it:

git switch -c my-topic
git add -A && git commit -m "Add notes"
git push origin my-topic

jj commit -m "Add notes"
jj bookmark create my-topic -r @-
jj git push --bookmark my-topic

When you push a branch to your fork, Git (or jj) prints a link to the original's compare page with your fork preselected; the fork's front page shows the same link in its "Recently pushed" banner, and Contribute next to "Forked from" opens the compare page too. There, From picks the repository (your forks of the network that you can push to) and Merge its branch. Through the API:

POST /api/v1/repos/<owner>/<repo>/merge-requests
{"source_repo": "<you>/<fork>", "source_branch": "my-topic", "title": "…"}

The source can be any repository of the same fork network that you can push to. The original receives only the history of that branch, never your fork's other branches; until you open the merge request it holds nothing of your fork. Each push to the branch adds a revision, and the merge request merges like any other. Merging leaves your fork's branch as it is.

If your fork is less visible than the original (a private fork of a public repository, for example), everyone who can read the original will be able to read the merge request's commits. Slath asks you to confirm that (Make these commits readable here on the compare page, "publish_source": true in the API) and notes it in the merge request's timeline.

The original's push protection checks every push to the branch before the merge request takes it over, even if your fork has push protection off. If it finds a possible secret, the merge request stays at its previous revision and shows what was found. Remove the secret and push again, or ask a writer of the original to allow it if it isn't one.

Edits by maintainers

A merge request from a fork allows edits by maintainers unless you turn it off: uncheck Allow edits by maintainers on the compare page, use More → Stop allowing edits by maintainers on the merge request, or send "allow_maintainer_edits": false through the API. While it's open, anyone who can write to the original can then push to your merge request's branch in your fork, for example to fix a typo before merging. They can only update that one branch: they can't delete it, push other branches or tags, or change anything once the merge request is closed or merged. Only someone who can push to your fork can change the setting, and each such push is recorded in the original's audit log.

The right only goes from the original to forks of it: a merge request from the original into your fork gives you no access to the original.

The branch mr/<n> in the original

While a merge request from a fork is open, the original shows it as the branch mr/<n> (mr/12 for merge request 12) at its latest revision. That way reviewers check it out, and maintainers push edits to it, with Git or jj and without adding your fork as a remote. It appears in the fetches of its requested reviewers and assignees, of anyone who used Check out on it, and, for pushing, of those who may edit it; everyone else's fetches don't show it, and it disappears when the merge request is closed or merged. That's to keep fetches tidy, not to keep it secret: whoever can read the original can read the merge request's commits.

A push to mr/<n> by someone who may edit the merge request as a maintainer updates your branch in your fork, by compare-and-swap: if you pushed meanwhile, their push is refused or its output says it didn't reach the fork, and they fetch and try again. Nobody else can push to mr/<n>, and no other branches can be created under mr/.

Git sends credentials over HTTPS only when a server asks, so fetches of a public or internal original are anonymous and don't show mr/<n>. Use the address that always asks, https://slath.example/-/auth/<owner>/<repo>.git, which Check out and POST …/merge-requests/{n}/checkout give you; over SSH it works with the usual address.

On the merge request, Check out → Check out mr/ adds the branch to your fetches; the menu then shows the commands. For merge request 12 in your clone of the original:

git fetch https://slath.example/-/auth/alice/demo.git mr/12:mr/12 && git switch mr/12

jj git remote set-url origin https://slath.example/-/auth/alice/demo.git && jj git fetch --branch mr/12 && jj bookmark track mr/12@origin && jj new mr/12

To edit it as a maintainer, commit and push the branch; the fork's branch follows:

git add -A && git commit -m "Fix a typo"
git push https://slath.example/-/auth/alice/demo.git mr/12

jj commit -m "Fix a typo"
jj bookmark set mr/12 -r @-
jj git push --bookmark mr/12
