A self-hosted code forge where Git and Jujutsu users work on equal terms

Slath is a code forge you run yourself: repositories, merge requests, reviews, and issues for your team and the agents you run. It needs Slath, PostgreSQL, Git, and OpenSSH, and nothing on the internet. It's free software under the AGPL.

Sandbox on your computer

A throwaway Slath with an administrator, an organization, a repository, and a bot. It isn't for production: its database password is fixed, and it has no TLS.

  1. Download the release's Compose files and start the sandbox:

    curl -fsSL https://github.com/slath-org/slath/releases/download/v0.3.0/slath-compose-0.3.0.tar.gz | tar -xz
cd compose/agent-sandbox
docker compose up -d
docker compose logs seed   # wait for "Slath agent sandbox"

  2. Open 127.0.0.1:3080 and sign in as ada, with the password from this file:

    cat secrets/ada-password

  3. Push to sandbox/playground as the bot agent. After the push of a branch, Git prints the link to open a merge request for it. With jj, clone with jj git clone and the same address.

    git clone "http://agent:$(cat secrets/bot-token)@127.0.0.1:3080/sandbox/playground.git"
cd playground
echo "# Playground" > README.md
git add README.md && git commit -m "Add a README"
git push origin HEAD:main
git switch -c say-hello
echo "Hello." >> README.md && git commit -am "Say hello"
git push origin say-hello

  4. To start over, remove the sandbox and its data from the agent-sandbox folder:

    docker compose down -v && rm -f secrets/*

With Podman, write podman compose where it says docker compose.

Docker Compose

PostgreSQL, Slath, and sshd from the published image, which brings its own Git and OpenSSH. Nothing is built on your computer.

  1. Download the release's Compose files and set the database password:

    curl -fsSL https://github.com/slath-org/slath/releases/download/v0.3.0/slath-compose-0.3.0.tar.gz | tar -xz
cd compose
printf 'SLATH_DB_PASSWORD=%s\nSLATH_PUBLIC_URL=http://localhost:3000\n' "$(openssl rand -hex 24)" > .env

    For a server, set SLATH_PUBLIC_URL to the address people use. .env.example lists the other settings.

  2. Start Slath and create the first administrator, with your own name. The password is printed once.

    docker compose up -d
docker compose run --rm slath admin create-user --admin \
    --username ada --email ada@example.org

  3. Open localhost:3000 and sign in. Administration needs two-factor authentication: set it up under Settings → Security. Then create a repository and clone it over HTTPS with an access token, or over SSH on port 2222 with your key.

  4. Copy the master key somewhere safe, apart from your backups:

    docker compose cp slath:/var/lib/slath/master.key ./master.key

With Podman, write podman compose where it says docker compose. For TLS, the Compose files run Caddy with --profile tls.

Installing with Docker Compose

Linux server

For a host with systemd and glibc 2.41 or newer, such as Debian 13, Ubuntu 25.04, or Fedora 42. Install PostgreSQL 15 or newer with its contrib modules, Git, and OpenSSH from your distribution first.

  1. Download the binary, check its signature with the GitHub CLI, and install it. On ARM servers, use aarch64 in place of x86_64.

    v=0.3.0
gh release download "v$v" --repo slath-org/slath --pattern "slath-$v-x86_64-linux"
gh attestation verify "slath-$v-x86_64-linux" --repo slath-org/slath \
    --signer-workflow slath-org/slath/.github/workflows/release.yml \
    --source-ref "refs/tags/v$v"
sudo install -m 0755 "slath-$v-x86_64-linux" /usr/local/bin/slath

  2. See what setup would do, then let it create the users, the database, the service, the sshd configuration, and the first administrator:

    sudo slath setup --check --public-url https://git.example.org
sudo slath setup --public-url https://git.example.org \
    --admin-username ada --admin-email ada@example.org

  3. Forward HTTPS for your address to 127.0.0.1:3000 with your reverse proxy, and copy /etc/slath/master.key somewhere safe, apart from your backups.

What Slath does

Slath 0.3 covers the daily work of a team: code, merge requests, reviews, forks, issues, and the bots that help with them.

For reviewers

Merge requests that follow each change

Every push to a merge request is a new revision. Slath matches each commit to the change it belongs to, so after a rebase or an amend you see what changed since your review, not the whole diff again. Approvals stay when a rebase keeps every patch and go stale when the content changes.

The page opens with what decides the merge: one headline, the reason, and your next step. Review threads, suggestions you can apply, required checks with their reporters, and merge when ready are all there.

Merge requests guide

For Git and jj users

One workflow for both tools

A team can mix Git and Jujutsu freely. Slath recognizes a change by its jj change ID, a Change-Id trailer, an identical patch, or similar content, so nobody installs hooks, adds trailers, or configures a client.

A change looks the same whichever tool made it. Commands on the page follow the tool you use, and every guide shows Git and jj side by side.

Working with changes

For contributors

Forks without friction

Fork a repository, keep it in sync, and open a merge request into the original. Maintainers can push fixes to your branch unless you turn that off, with Git or jj.

Forks guide

For administrators

Update by restarting

Install the new version and restart. Slath checks the installation, backs it up, and migrates, or refuses to start and changes nothing when it can't update safely. Daily backups and slath doctor keep it healthy.

Upgrading guide

For security teams

Boundaries you can check

SSH logins run as their own system user that never reaches the database, keys, or repositories. Push protection rejects secrets before they're stored. Releases are signed with Sigstore and carry their build provenance.

Push protection

For teams with AI agents

Agents propose, people merge

Slath runs no agents and no models. It gives the agents you run an identity of their own and only the access they need.

  • One bot per agent, with tokens for named repositories that expire after 30 days.
  • Sensitive paths such as CI workflows and AGENTS.md are off limits to bots.
  • A bot's merge request iterates quietly and asks for review once its checks pass.
  • Stopping a bot revokes all its credentials at once.
Working with AI agents

For integrators

An API, webhooks, and checks

A REST API with a reference for every endpoint, so your CI and tools connect without plugins.

  • Webhooks for pushes, merge requests, reviews, issues, and statuses, signed and retried.
  • Commit statuses that branch protection can require, with line annotations shown as findings.
  • slath admin apply sets up users, organizations, bots, and repositories from a file.
API reference

For everyone who runs it

Small, and self-contained

One Rust binary, PostgreSQL, Git, and the OpenSSH server you already run. No Kubernetes, no Redis, and no hosted account. Every font, icon, and script comes from your instance, avatars are never fetched from another service, and each installation serves the documentation of its own version at /-/docs/, offline too.

Scope

Not in 1.0

Federation, a package registry, Git LFS, wikis, code search, and Kubernetes-native high availability. Some of them may come after 1.0.

Federation

ForgeFed after 1.0

Slath 1.0 doesn't federate. Experiments with ForgeFed are planned for 2.x; the AT Protocol and Tangled are a research topic, not a commitment. Until then, Slath builds what federation depends on: stable change identity, a complete API and webhooks, and full data export.
