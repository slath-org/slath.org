A self-hosted code forge where Git and Jujutsu users work on equal terms

Slath is a secure, lightweight forge you run yourself. A small installation needs only Slath, PostgreSQL, Git, and OpenSSH. It's free software under the AGPL.

Slath 0.2 is out: the team alpha. It adds issues with a rich-text Markdown editor, notifications, search, single sign-on with OpenID Connect, passkeys and two-factor authentication, teams, branch protection, internal repositories, import from other Git servers, and one-command upgrades. Running 0.1? slath upgrade takes you there; read the upgrade guide first, since administrators now need two-factor authentication. Before 1.0, minor releases may change configuration, storage, and interfaces.

For self-hosters

Small enough to run on one machine

Slath is a single Rust binary. It doesn't need Kubernetes, Redis, a hosted account, or anything on the internet once it's installed.

  • Four parts, all of them familiar

    Slath, PostgreSQL, system Git, and the OpenSSH server you already run. Background jobs use a queue in PostgreSQL. Repositories, attachments, and avatars live on the local filesystem. Email is optional.

  • Security boundaries you can check

    Git runs only through a hardened process runner with a scrubbed environment. SSH logins run as a separate system user that can only reach the server's socket, never the database credentials, keys, or repositories. Hooks that can't reach the server reject the push instead of letting it through. CI jobs run on separate runner hosts, never on the forge.

  • Self-contained and air-gap friendly

    Every font, icon, and script is served by your instance. No CDNs, remote fonts, analytics, or avatar services: avatars are uploaded or generated, and stored without their metadata.

  • Backups and one-command upgrades

    slath backup create takes a consistent backup while the server runs, and slath backup restore checks it fully before writing anything. slath upgrade goes from any earlier release to the current one in one step: preflight checks, an automatic backup, migrations, and verification. If it's interrupted, running it again finishes the job. Every release is tested against upgrades from all earlier ones.

For Git and Jujutsu users

Review changes, not just branches

Plain Git clients clone, fetch, and push over HTTPS and SSH with the standard protocols. Jujutsu is first-class too: Slath follows a change across rewrites, so reviews survive rebases and amends.

A change keeps its identity however often you rewrite it. Slath reads that identity from either of two places:

  • the change-id header that jj writes into Git commits, or
  • a Change-Id: trailer in the commit message, for Git users and existing Gerrit-style tooling.

On top of that, merge requests will show each revision of a change, interdiffs between revisions, and stacks of dependent changes that can be reviewed one by one and landed partially, from the web or by pushing.

Merge requests and stacks are planned. Slath 0.2 serves Git over smart HTTP (protocol v0 and v2) and over SSH, and its test suite runs jj git clone and jj git push over both for every supported jj version.

Federation

ForgeFed: after 1.0, on solid ground

Slath 1.0 won't federate. We'd rather say that plainly than promise a half-working protocol.

ForgeFed lets issues, merge requests, and follows cross instance boundaries. Experiments with it are on the roadmap for the 2.x series. Interoperability with the AT Protocol and Tangled is a research topic, not a commitment.

Until then, Slath builds what federation depends on:

  • Stable change identity that doesn't break when a commit is rewritten, so a change can be referred to from elsewhere.
  • A complete REST API and webhooks, so other systems can follow what happens on an instance.
  • Full data export, so nothing you put into an instance is locked in.

If you work on ForgeFed, run a federated forge, or have opinions on how jj change identity should travel between instances, we'd like to hear from you early, while the data model is still open.
